# PierOps 后续开发路线（执行版）

版本：2026-09-27。定位：单组织、自托管、以 Agent 主动连接 Hub 为核心的轻量可控运维平台。先交付可验证的安全基线，再逐步开放高权限操作。

## 交付原则

- 每个阶段都在 `docs/DEVLOG.md` 留下实际改动、验证证据和未完成项，并形成独立提交。
- Hub 可本地二进制运行，也可由 Docker/Compose 运行。Hub 容器**不挂载 Docker socket**；节点 Docker 信息由 Agent 在节点本机读取。
- 公开仓库只包含可以公开的源码、文档和构建脚本。凭据、数据库、用户文件、测试录制、构建产物和未经确认可再分发的前端源码都不进入公开 Git 历史。
- 阶段产物交给用户在自己的 VPS 上验证；本地验证优先使用临时目录或独立副本，避免污染正式数据。

## 里程碑

| 阶段 | 开发范围 | 交付产物与完成条件 | 粗估 |
| --- | --- | --- | --- |
| M0 发布与运行基线 | 公开仓库卫生检查；前端固定版本外部构建；Hub 多阶段 Dockerfile、Compose、持久化数据、健康检查；本地脚本 | 干净的公开 Git 历史、公开 GitHub 仓库、可拉取源码构建 Hub 镜像；隔离安装页和重启后数据持久化验证 | 2–4 天 |
| M1 授权骨架 | 用户—节点—动作权限模型；统一授权入口；拒绝审计；现有终端/文件/命令入口接入 | 无权限用户不能通过 REST、RPC 或 WebSocket 绕过；权限变更有日志和测试 | 1–2 周 |
| M2 Agent 本地约束 | 能力开关、受限目录、终端运行用户、短期操作票据、协议去重/过期 | Hub 误发或重放请求时 Agent 拒绝；文件不能逃出允许目录 | 1–2 周 |
| M3 Docker 只读 | Agent 本机 Docker API 适配器；容器列表、详情、状态、有限日志和指标；Hub 页面 | 无 Docker/无 socket 权限可解释；只读授权无法触发写操作；Hub 不访问 Docker socket | 1–2 周 |
| M4 审计与交付 | 终端会话录制/回放、操作检索、备份恢复、Linux Agent 安装包、Hub 镜像版本与升级说明 | 隔离环境完成重启、恢复、断线与权限回归；提供用户测试包和测试清单 | 2–3 周 |
| M5 受控写操作（按测试结果决定） | 文件写入细化、Docker 启停、审批或二次确认 | 操作逐项授权、可追溯、可撤销或说明不可撤销，经过用户真实环境验证 | 另行估算 |

估算按一名开发者、复用现有 Komari Hub/Agent/Web UI、Linux VPS 单 Hub、5–50 节点计算。M1–M4 的顺序可因真实测试反馈调整；M0 是公开发布和后续验证的前置条件。

## 本轮从 M0 开始的任务

1. **仓库清理：** 核查所有可达 Git 提交与待发布文件；让前端由固定上游 commit 在构建时获取；重建仅含可公开内容的发布历史；在本地添加远端并推送公开 GitHub 仓库。
2. **Hub 容器：** 多阶段构建前端和 Go Hub；非 root 运行；数据卷、监听地址和健康检查明确；Compose 默认仅发布到主机 `127.0.0.1`，需要 LAN/反向代理时可配置。
3. **验证：** 本地 `make test`、镜像构建、容器安装页、数据重启持久化、源码/历史敏感信息扫描。Docker 引擎若在当前环境不可用，完成 Dockerfile/Compose 静态校验并在交付中明确未做容器运行验证。
4. **用户验收：** 交付公开仓库链接、固定提交、运行命令和独立测试目录/端口说明；用户在 VPS 上验证后再进入 M1 或修复反馈。

## 验证关口

- **公开发布前：** `git status` 干净；检查 Git 历史和当前树的高置信凭据模式；确认 `.env`、数据库、构建产物未跟踪；检查依赖源码许可与来源说明。
- **M1：** 对每一种敏感传输入口做未授权、跨节点和过期会话测试。
- **M2：** Agent 本地路径边界、符号链接、重放与断线恢复测试。
- **M3：** Docker Engine 版本兼容、socket 不可用、超大日志和只读权限测试。
- **M4：** 录制完整性、敏感信息处理、备份恢复与升级回滚演练。

## 本轮不包含

公开生产部署、真实 VPS 凭据配置、多租户、高可用、Windows Agent、Kubernetes、Docker 写操作。上线验证由用户在实际环境执行，结果进入下一轮开发日志。
